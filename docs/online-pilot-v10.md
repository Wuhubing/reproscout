# Authenticated online execution pilot

## Delivery status

The online application is implemented and has passed a real authenticated browser workflow on the development host. A durable public execution deployment is **pending server access and final hosting cost confirmation**. The existing GitHub Pages site remains the public read-only evidence archive. No VM, domain, or hosting subscription has been purchased.

This release adds an invitation-only service: sign in, upload a prepared project ZIP, run original code, inspect evidence, save question-level reviews, export a portable report, and sign out. Accounts have independent project, job, run, lesson and review directories. Uploading an arbitrary repository does not automatically resolve its dependencies; a verified input bundle and an operator-approved runtime are required.

## Architecture

The same production React client is served by the online backend under one HTTPS origin. Caddy terminates HTTPS and proxies to a loopback-only backend. This avoids cross-site cookies, browser-held bearer credentials, and permissive CORS. GitHub Pages cannot host this process; its archive remains separate and can link to the execution service once an actual domain is provisioned.

The host keeps an SQLite account/session/reservation database plus persistent per-account directories. High-entropy access codes are generated by an operator and stored only as SHA-256 hashes. Session cookies are HttpOnly, SameSite=Strict, Secure on HTTPS, and expire after twelve hours. Login attempts are rate-limited globally. Mutations require both the configured origin and a CSRF token. Logout and account revocation invalidate server-side sessions. Reviewer identity is bound to the authenticated account; the human/assistant distinction is retained.

One controller runs across all accounts at a time. A busy server rejects another launch explicitly; this version does not claim a durable job queue. Existing worker processes are checked after restart; interrupted attempts remain visible, and no task is silently retried. Reports and review versions remain on disk across restarts. Only approved digest-pinned images are accepted, and a missing image must be provisioned by the operator. Containers retain the existing offline network, capability, process, memory and CPU restrictions.

This is a trusted, invited research pilot on a dedicated host. Docker shares a host kernel and the controller has Docker access; it is not a hardened anonymous arbitrary-code service. The HTTP backend is behind a reverse proxy, not exposed directly. Admission checks limit accounts to ten imported projects and pause mutations/runs once recorded workspace size exceeds 500 MiB. That check is not a hard runtime filesystem quota. Operators need disk monitoring and retention management; no evidence is automatically deleted to recover space.

## Budget

The user requested a US$5 monthly budget. Server, tax, domain and model charges must all be considered before purchase. As checked on November 19, 2026, [OVHcloud's US page](https://us.ovhcloud.com/vps/) advertises VPS-1 from $4.54/month with 2 vCores, 4 GB RAM and 40 GB NVMe. This is a candidate, not a verified checkout quote; commitment terms, tax and available region may change the total. No budget increase is assumed.

The backend caps each model reservation at $0.10 and defaults to a $1 host-wide monthly reservation ceiling. Reservations are conservative and are not refunded automatically, including uncertain failed launches. Actual estimated model cost remains reported separately for every run. For a strict $5 total budget, the deployment operator must set the model ceiling to the actual remaining balance after the final hosting bill, or defer deployment if there is no remaining balance. The service file accepts a configured monthly ceiling; it does not cap the cloud provider invoice. API-provider accounting and price changes may differ from estimates.

## Run on a development host

Install the locked dependencies and build the regular frontend. Provision the approved image in `deploy/images.example.json`. Use a state directory outside public report exports.

```sh
uv sync --locked --extra dev --python 3.12
npm ci --prefix frontend
npm --prefix frontend run build
mkdir -p private
uv run python -m reproscout.online \
  --state private/online-pilot --origin http://127.0.0.1:8780 \
  --images deploy/images.example.json \
  --invite researcher --code-file private/researcher-access.txt
uv run python -m reproscout.online \
  --state private/online-pilot --origin http://127.0.0.1:8780 \
  --images deploy/images.example.json --monthly-model-budget 0.10 \
  --key-file /secure/path/to/api-key.txt
```

Open `http://127.0.0.1:8780`, sign in using the access code, and upload the supplied example ZIP. The access code is not an API key. Never place either credential in a repository, query string or public report. The operator can create further accounts while the service runs. To revoke an account, use the same command configuration with `--revoke researcher`; retained data is preserved, and active jobs are not automatically cancelled.

## Dedicated Linux deployment

Use an amd64 Linux VM with enough disk for the approved images, at least 4 GB RAM for this 2 GB sandbox plus host processes, Docker Engine/Compose, Python 3.12, and Caddy. Image sizes and download availability must be checked on the actual host before claiming deployment success.

1. Install the source and locked Python environment at `/opt/reproscout`; build or use the checked-in production frontend. Keep source owned by the administrator and readable by the service account.
2. Place the operator-approved image list at `/etc/reproscout/images.json`; explicitly pull each pinned image as an administrator. Do not allow uploaded manifests to trigger arbitrary image pulls.
3. Create root-readable `/etc/reproscout/server.env` with `REPROSCOUT_ORIGIN=https://your-hostname`, `REPROSCOUT_MONTHLY_MODEL_BUDGET` set to the remaining model allowance, and `OPENAI_API_KEY` supplied through a private channel. Do not put credentials into command history.
4. Run `deploy/install-service.sh`. It creates the service account/state directory and installs the systemd service. It does not buy infrastructure, install dependencies, overwrite Caddy, or obtain credentials.
5. Configure `deploy/Caddyfile` with the actual hostname, validate it with Caddy, and reload the proxy. DNS must point to the server and ports 80/443 must reach Caddy. Only loopback port 8780 reaches the backend. Use firewall restrictions on SSH.
6. Create an account with the server CLI while running it as the service user, with matching state, template, origin and image-list arguments. Deliver the generated access code privately.
7. Perform the browser acceptance workflow over the actual public HTTPS URL, verify cookie flags, log out, and verify unauthenticated report requests return 401. Restart the backend and verify persisted projects/reviews. Only then link the public execution URL from GitHub Pages.

Back up the SQLite database and per-account folders consistently; stop the service and ensure workers finish before a filesystem snapshot, or use SQLite's backup facility and a coordinated file snapshot. Keep backups private. Do not copy tenant state to the Pages exporter or the public report directories.
